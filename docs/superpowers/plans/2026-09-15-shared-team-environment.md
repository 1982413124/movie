# Neonを使ったチーム共有環境の実装計画

> このセッションで順に実装・検証する。ローカルの稼働DBをテストで変更しない。

**目的:** 管理画面から追加した映画と画像を、チーム全員が同じDBから取得する。

**構成:** PostgreSQLをNeon Freeで共有し、Next.jsとFlaskは各自のPCで動かす。小容量の作品画像は`movie_images`テーブルにWebPで保存する。画像URLと予約APIは維持する。既存のローカル保存は既定のまま残す。

**DBへの影響:** `movie_images(filename, content, created_at)`を追加する。予約・座席・ポイント・クーポンの既存制約やトランザクションは変更しない。現行DBをバックアップし、新しい空の共有DBに復元してから、この追加マイグレーションと画像の取り込みを一度だけ実行する。

- [x] `backend/movie_image_storage.py`に保存先の切替、取得、既存画像の取り込み、未使用画像の削除を追加する。取り込み時は同名の異なる内容を上書きせず、全体をロールバックする。
- [x] `backend/movie_routes.py`を保存先に依存しない形にする。管理者・CSRF・画像検査・URL形式・キャッシュは維持する。
- [x] `backend/database/shared_images_migration.sql`と`DDL.txt`を揃え、`manage.py migrate`から追加する。
- [x] `docker-compose.shared.yml`と設定例を追加する。共有環境の通常起動ではマイグレーションを実行せず、古い各自DBは起動対象に含めない。
- [x] `docs/TEAM_SHARED_ENVIRONMENT.md`に管理担当の移行手順と各メンバーの起動・停止手順を書く。DB接続文字列、メールAPIキー、バックアップをGitに含めない。
- [x] 専用のPostgreSQLテスト環境で、別APIからの画像取得、認証・画像検査、取り込みの再実行と衝突、既存の予約・仮押さえ・キャンセル・ポイント・クーポン・メール処理を確認する。
- [x] 元DBのバックアップの復元と画像ハッシュ・件数の照合をローカルの隔離環境で実施する。
- [x] Neonのアカウントと接続先が用意できたら共有DBへ移行し、別API経由でも同じ映画・画像・座席状態を取得できることを確認する。

## 無料枠の運用

2026-09-15確認時、Neon Freeは1プロジェクト0.5GB、月100 CU-hours。メールワーカーは10秒ごとにDBを確認するため、開発終了時は各自のAPIとワーカーを停止する。画面を開き続けた座席の定期取得も稼働時間に含まれる。常時稼働が必要になった段階で、メールの起動方式やプランを見直す。

共有するのは一つのNeonプロジェクト内の同じブランチ・DB。個別ブランチは変更の自動同期には使わない。画面は再読込または再フォーカスでカタログを取得し直す。

## ローカル検証結果

2026-09-15、隔離したPostgreSQL 16で既存機能と追加機能の111件が成功。実データのバックアップを非スーパーユーザー権限で復元し、映画2件・上映95件・予約13件を確認した。画像4枚のSHA-256が元ファイルと一致し、異なる2つのAPIから同じ作品一覧と画像を取得できた。画像の再取り込みは変更なし、使用済みDBへの再復元は拒否された。

## 共有先での確認結果

Neon Freeの`hal-cinema-team`（PostgreSQL 16、Singapore）へ移行した。移行前にAPIとメールワーカーを停止し、元DB・画像の最終バックアップを取得。クライアントのTLS接続を確認し、復元・追加マイグレーション・画像取り込みを実施した。元の22テーブルすべてについて、件数と全レコードのSHA-256が一致した（追加マイグレーションの記録1件を除く）。

異なる2つのAPIと3000のNext.jsプロキシから、同じ映画2件、画像4枚、200席の座席状態を取得できた。画像は全経路で元ファイルのSHA-256と一致した。ブラウザーでも、ちいかわのポスターと上映回が表示され、コンソールエラーがないことを確認した。既存のResend設定はローカルの`.env.shared`へ引き継ぎ、元のDBと元の`.env`は残している。
