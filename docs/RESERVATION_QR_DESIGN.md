# 予約QRの設計方針

## 現状

現在の予約APIには、予約QR、公開用トークン、読取API、失効処理がありません。予約IDは内部の連番で、予約取得もメールアドレスを指定する方式です。この状態でQRを表示すると、推測しやすいIDや個人情報をコードへ入れる危険があるため、今回の画面にはQRと表示ボタンを追加していません。

## 1予約1トークン

QRは予約ごとに1種類だけ発行します。入場、予約確認、フード受取、店頭でのポイント付与は同じトークンを読み取り、読取端末の用途に応じてサーバー側が処理を分けます。

- 32バイト以上の暗号学的乱数を使う
- QRにはランダムな公開トークンだけを入れる
- 内部予約ID、ユーザーID、メール、電話番号、支払い情報を入れない
- DBには平文トークンではなくハッシュを保存する
- キャンセルと返金で無効化する
- 再発行時は旧トークンを失効する
- 上映と受取が終わった後に有効期限を迎える

想定テーブルは `reservation_qr_tokens` です。最低限、`reservation_id`、`token_hash`、`status`、`issued_at`、`expires_at`、`revoked_at` を持たせます。入場とフード受取の状態はトークン自体を使い捨てにせず、用途別の処理履歴として保存します。

## API

QR表示前に、メールアドレス指定ではなくサーバー側で本人確認できるセッション認証が必要です。

- 会員向け: 認証済みユーザーが自分の予約QRを取得するAPI
- 読取端末向け: 端末認証と用途を受け取り、トークンを照合するAPI
- 管理向け: 失効と再発行を行うAPI

読取APIは `admission`、`food_pickup`、`point_earn` などの端末用途を受け取り、必要最小限の予約情報だけを返します。

## 表示場所

実装後は、次回予約カードの「予約QRを表示」からモーダルまたはスマートフォン全画面へ開きます。同じQRをマイページの予約詳細にも表示し、「入場時とフード受取時に提示してください」と案内します。会員情報タブにはQRやバーコードを置きません。
